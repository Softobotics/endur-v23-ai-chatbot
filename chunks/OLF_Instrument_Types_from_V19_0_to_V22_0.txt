The following description is directed towards OpenJVS developers.</p><p>The main issue seems to lie around `Transaction.getTranFromIns()` and `Transaction.getInsFromTran()`. The object that should be disposed is the "original" object. For example, if you perform an `Instrument ins = Instrument.retrieve()`, `ins.dispose()` should be called when the object is no longer needed. If `Transaction tran = Transaction.getTranFromIns(ins)` is called after the Instrument is created, the Instrument still owns the memory, and the Transaction is just an accessor object, and the call to `tran.dispose()` will have no effect.</p><p>One of the implementations that causes issues is to do something similar to `Transaction tran = Transaction.getTranFromIns(Instrument.retrieve(insNum));`. In essence, what happens here is the retrieved Instrument owns the memory (not the Transaction) and goes instantly out of scope (anonymous declaration). This means that it can be garbage collected at any point thereafter and may result in an application error when manipulating/accessing methods on the Transaction as the underlying memory has been freed. This can happen in the inverse scenario, as well: `Instrument ins = Transaction.retrieve(tranNum).getInsFromTran()`, though this seems to happen far less often.</p><p>To aid developers in these scenarios, we created methods to provide better control of the memory management: `Transaction tran = Transaction.getTranFromInsChangeOwner(ins)` and `Instrument ins = Transaction.getInsFromTranChangeOwner(tran)`. In both cases, the passed in argument will give up its memory ownership and pass it to the returned object. This returned object can then be disposed as before.</p><p>Also, we added Transaction retrieval methods using an Instrument Number to reduce multiple method calls. The methods are `Transaction.retrieveFromInsNum(insNum)` and `Transaction.retrieveCopyFromInsNum(insNum)`. Both scenarios return a disposable Transaction with the same logic of `Transaction tran = Transaction.getTranFromInsChangeOwner(Instrument.retrieve(insNum))`</p><p>Finally, as part of this effort, we have logged messages to the OConsole output when an object is disposed during the `finalize()` method. In essence, this is saying that the object held on to resources that object has gone out of scope. While this memory is not "leaked", it will only be released at some future undetermined time (for example, when the garbage collector decides to run). To aid in determining which object was not properly disposed, the Stack Trace of when the object was created can be added to the message by turning the "General" Debug Type to "Low".</p></td><td style="border-right: solid 1pt #000000; border-bottom: solid 1pt #000000; mso-border-alt: solid windowtext .5pt; padding: 0in 2.15pt 0in 2.15pt; border-image: none; padding-left: 0px; padding-top: 0px; padding-right: 0px; padding-bottom: 0px; vertical-align: Top;" width="81">157079</td></tr></table>

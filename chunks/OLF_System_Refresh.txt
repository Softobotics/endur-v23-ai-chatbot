# OpenLink System Refresh

## Overview

This document describes the ability of OpenLink Endur/Findur to 
	 ensure that it uses the most current data.  This functionality 
	 differs from version to version in terms of the features, the setup 
	 requirements, and the underlying technology.

## Approaches To Data Access

One approach to data access is to always load data as needed from 
	 the central data store, the database.  This is a simple 
	 approach and it ensures data is up to date at all times, but it is 
	 very bad in terms of performance.  An alternative to this 
	 approach is to implement a data caching functionality.  A 
	 data cache is data kept in local memory for when it will be needed 
	 in the future.  Accessing data from local memory is faster 
	 than accessing the same data from the database.   Data 
	 retrieved from the database involves a network message to be sent 
	 to and from the database, which is a delay.  Also, because 
	 of the shared nature of the database resource, it is advisable to 
	 limit hits to the database and a data cache helps with this.

In the simplest case, pick list data does not change.  For 
	 example, if you have a pick list with just two values of “Yes” and 
	 “No” and the user can’t add more values.  For the simplest 
	 case, a system could load all data at startup into the cache and never 
	 need to worry that the cache is out of date.  In a more 
	 complicated case, you may have a pick list, such as the counterparty 
	 pick list, where users can add additional values.  Without 
	 special functionality to know about changes, a cache can become out 
	 of date, in other words, hold a copy of older information.

## Data Caching Mechanisms in Endur/Findur

All versions of the Endur/Findur have some kind of data caching.  In 
	 earlier versions, this cache is called Shared Memory.  In 
	 later versions this technology is called the Cache Engine, which has 
	 several important features that Shared Memory lacked.  It 
	 is more efficient because it only loads data when needed.  Also, 
	 it can add memory dynamically as needed, while Shared Memory was limited 
	 to a predefined amount.

## Notes About ANE

ANE is used by the system in all versions for

So a client that uses and of the above modules must run ANE in all 
	 versions.

ANE is also used to automatically update

Having these modules auto-update is optional and clients using these 
	 may choose to not run ANE.  They would just need to manually 
	 refresh queries as needed.

In V7.0 and below, ANE is used to update market data (such as prices/rates) 
	 on other user’s machines when these are changed.  This updating 
	 is optional and clients not wanting to take advantage of this feature 
	 would not need to run ANE.  Clients would just need to manually 
	 reload data as needed.  In V8.0, this is was redesigned 
	 to that the Cache Engine automatically updates market data without 
	 the need for running ANE.   Note: This is tentatively 
	 planned as of November 16, 2004 and expected to make it into V8.0, 
	 but it is not in V8.0 yet.  So as of November 16, 2004 users 
	 still need to use the V7.0 method.

Notes:

When data is needed, the system always checks 
 the Cache Engine to get the data.
If the data was never loaded into the data 
 cache, or if it has been invalidated, then the Cache Engine retrieves 
 the data from the database and delivers it to the requestor.  The 
 Cache Engine also adds the data to its cache for future requests
The Cache Engine invalidates data when it 
 receives notice that the data has been updated (so any cached 
 data would be out of date).

There is an AVS function in 8.0r1 and up 
 called UTIL_RefreshCache.  It allows users to write 
 a script that will force a refresh of the cache.  It 
 would not normally be needed and was only added to the system 
 as a contingency.
The cache engine has a feature that allows 
 it to discard older data in the cache.  This allows 
 the total memory of the cache to be kept within a reasonable size.  This 
 process is transparent to the end user.

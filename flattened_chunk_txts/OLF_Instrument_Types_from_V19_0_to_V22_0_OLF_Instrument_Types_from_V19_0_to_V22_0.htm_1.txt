| Multileg Bond Asset Backed 
		 Security | BOND-ABS-ML | 9050 | This 
		 enhancement introduces a Bond toolset instrument type BOND-ABS-ML 
		 "Multileg Bond Asset Backed Security". This instrument 
		 type models principal prepayments like the BOND-ABS, but uses 
		 a new, generalized Prepayable leg type. Both prepayment projections 
		 and published factor fixings are supported. Prepayable legs may 
		 be chained together with contiguous, non-overlapping follow-on 
		 legs. A BOND-ABS-ML holding instrument may have an amortization 
		 style and prepayment projector, both of which carry across all 
		 follow-on legs. Follow-on legs may have different payment terms, 
		 basis, and frequency. The BOND-ABS-ML supports floating rate caps 
		 and floors, and each leg may be extended with issuer call options. 
		 Market facing calculations for trades in BOND-ABS-ML may include 
		 yield, discount margin, or trading margin based on varying termination 
		 dates. These are configured in the Yield To parameter of the Bond 
		 holding instrument as yield to Maturity, Next Leg, or WAL. Also, 
		 the instrument supports floating rate legs for the yield convention 
		 Benchmark Composite. In this case, Yield is simply the sum of 
		 the Discount Margin and Assumed Rate of the benchmark index. The 
		 BOND-ABS-ML allows price type to be configured as Indexed, rather 
		 than using the Yield Calc Method "Standard Amortize" 
		 to drive price quote convention. The existing BOND-ABS (and BOND-ABS-S) 
		 instrument type is still supported and minimally changed.a) BOND-ABS-ML supports step-ups, but differently (as a follow-on 
		 leg)b) BOND-ABS-ML does not yet support the Default projection features 
		 of BOND-ABSc) Prepayment Curve Construction extensions are supported for 
		 both instrument types with an appropriate license.OpenJVS API Change for Transactions/Instruments): In V22_0, 
		 we introduced a change to manage the ownership of the created 
		 underlying memory in the core code. The following description 
		 is directed towards OpenJVS developers.The main issue seems to lie around `Transaction.getTranFromIns()` 
		 and `Transaction.getInsFromTran()`. The object that should be 
		 disposed is the "original" object. For example, if you 
		 perform an `Instrument ins = Instrument.retrieve()`, `ins.dispose()` 
		 should be called when the object is no longer needed. If `Transaction 
		 tran = Transaction.getTranFromIns(ins)` is called after the Instrument 
		 is created, the Instrument still owns the memory, and the Transaction 
		 is just an accessor object, and the call to `tran.dispose()` will 
		 have no effect.One of the implementations that causes issues is to do something 
		 similar to `Transaction tran = Transaction.getTranFromIns(Instrument.retrieve(insNum));`. 
		 In essence, what happens here is the retrieved Instrument owns 
		 the memory (not the Transaction) and goes instantly out of scope 
		 (anonymous declaration). This means that it can be garbage collected 
		 at any point thereafter and may result in an application error 
		 when manipulating/accessing methods on the Transaction as the 
		 underlying memory has been freed. This can happen in the inverse 
		 scenario, as well: `Instrument ins = Transaction.retrieve(tranNum).getInsFromTran()`, 
		 though this seems to happen far less often.To aid developers in these scenarios, we created methods to 
		 provide better control of the memory management: `Transaction 
		 tran = Transaction.getTranFromInsChangeOwner(ins)` and `Instrument 
		 ins = Transaction.getInsFromTranChangeOwner(tran)`. In both cases, 
		 the passed in argument will give up its memory ownership and pass 
		 it to the returned object. This returned object can then be disposed 
		 as before.Also, we added Transaction retrieval methods using an Instrument 
		 Number to reduce multiple method calls. The methods are `Transaction.retrieveFromInsNum(insNum)` 
		 and `Transaction.retrieveCopyFromInsNum(insNum)`. Both scenarios 
		 return a disposable Transaction with the same logic of `Transaction 
		 tran = Transaction.getTranFromInsChangeOwner(Instrument.retrieve(insNum))`Finally, as part of this effort, we have logged messages to 
		 the OConsole output when an object is disposed during the `finalize()` 
		 method. In essence, this is saying that the object held on to 
		 resources that object has gone out of scope. While this memory 
		 is not "leaked", it will only be released at some future 
		 undetermined time (for example, when the garbage collector decides 
		 to run). To aid in determining which object was not properly disposed, 
		 the Stack Trace of when the object was created can be added to 
		 the message by turning the "General" Debug Type to "Low". | 157079 |.
